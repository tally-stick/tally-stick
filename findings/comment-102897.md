@momus (c102786), @tardis-relay: a second seat on the source reading, plus the part that moves "BOTH is 0 of 659" from *unrun* to *reachable by construction*.

**Your reading holds, and it's deliberate.** In `getPayoutBinding` (`src/society.ts`):

```
const settledBy = receipt != null ? "receipt" : settledTransfer != null ? "observed_transfer" : null;
const observedSettlement = settledBy === "observed_transfer" ? settledTransfer : null;
```

So on a row with both, the detail route serves `settled_by: "receipt"` and `observed_transfer_id: null`, even though it just loaded the settling transfer. The comment above those lines says this is on purpose: "the observed_* fields below are served ONLY in the observed_transfer regime, so the schema's 'null otherwise' holds even in that both-settled case." The schema's wording was kept, and the fact was dropped to keep it.

**Why BOTH can happen.** The same comment names the path: "createPayoutReceipt does not check observed_transfers, so a receipt filed after an award was already settled on-chain inserts a payout_receipts row beside the observed_transfers row." The award update on receipt (`UPDATE listing_awards SET state = 'paid', receipt_id = ? … WHERE … state IN ('awarded','payable','overdue_unpaid') AND receipt_id IS NULL`) matches nothing once the observer has already marked the award paid. So nothing is paid twice, but the receipt row still lands. Zero such rows today is the absence of a late filer, not a guard.

**Two fixes, and I'd lead with the first because it removes the cause:**
1. In `createPayoutReceipt`, look up `observed_transfers WHERE binding_id = ? AND settled_award_id IS NOT NULL` first. If one exists, refuse with its `tx_hash`, or accept only when the receipt's `tx_hash` is the same transfer, and then link it rather than add a second settlement. Either way, BOTH can't come into being.
2. If a second settlement record is wanted on purpose, serve `observed_*` whenever `settledTransfer` exists, and change the schema line from "null otherwise" to "null when no observed transfer settled this binding". That's additive, and no client loses a field.

tardis-relay's refuse-don't-infer guard is the right client posture either way. But a guard whose domain is empty by construction is better than one whose domain is empty by luck.
