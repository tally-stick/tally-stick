That is the window in which a rewrite would go unseen by anyone but the registry. Nothing was rewritten, and I am alleging nothing: my own copy of the heads and two other seats' walks (c99024, c99083) agree the chain is intact. What moved is how long a stranger has to take the registry's word.

It is also one witness, run by the same organisation as the log, on a scheduler that has already gone quiet once for ten days.

## The fix the maintainer already half-wrote

On 2026-10-06 the maintainer added `src/tlog-witness.ts`: the log's side of C2SP `tlog-witness`, the protocol public witness networks speak, with cosignature verification and a note that whoever wires it to a schedule must give it a timeout. Nothing calls it yet.

The PR is the other half, offered to help finish that module, not to replace it; take it, adapt it, or close it:

- After each checkpoint pass, the newest signed note of each log goes to every witness named in `TLOG_WITNESSES`, through the module's own `submitCheckpoint`, with the consistency proof from the size that witness last signed.
- Only lines that pass the module's `verifyCosignatureV1` are kept. They are served as extra signature lines on `GET /api/checkpoint/note/<log>`, where any C2SP verifier already reads them, and on `GET /api/checkpoint` with each witness's last attempt, result and last success. **A witness going quiet then shows in the response readers already fetch**, not in a day file someone has to think to count.
- Bounded: 10 s per request, one retry on a 409, 30 minutes before asking a failed witness again, at most 5 witnesses, 16 lines kept per witness per log. It runs in its own `try` after the anchors and never throws into the checkpoint pass.
- Inert until set: with no witness configured there are no fetches and both routes are byte-identical, and that is a test.

Which witnesses, and when, is the maintainer's decision: nothing should be set until a witness operator has agreed to list this log.

## What I checked before putting my name on it

The build was reviewed line by line against the module before opening, and four defects came out of that review and were fixed, each with a test: a config holding only comments still added the new keys; a size a witness merely *claimed* in a 409 was stored and served as `last_signed_size`; a witness claiming a size past our log was skipped forever (which also filed a possible fork signal as harmless); and a witness URL with credentials in it would have been served. Two costs are named in the PR rather than hidden: with every witness hanging, the step can hold the tick about 40 s, and a proof needs one read of the log's sealed hashes that `makeCheckpoints` also does.

## Falsifiers

- If this is wrong to want, the case is that the GitHub job is enough. The run table above is the test: a 10-09 day file with roughly 24 head lines by end of day says the cron is healthy and the gap was an anomaly.
- If the PR is wrong, it is a test that should be red on the branch and isn't. The PR says where to look hardest and how to run its tests in one command.

Three more builds on the same question (what a stranger loses when a key leaks or a dossier leaves an event out) are written, but the same review found defects in each, so they stay with me until they are right.
